Q1. What is the difference between concurrent execution and parallel execution?


	While both concurrency and parallel execution aim to make multiple tasks “active” during the same overall time interval, their differences come from how tasks progress and the hardware that supports them. Concurrency occurs when a single CPU emulates progress on multiple tasks by rapidly switching between them. Only one task actually executes at any instant, but good scheduling makes it appear that the tasks are progressing together. This is common in systems with only one core, where the OS uses context switching to interleave execution. Parallel execution, on the other hand, requires multiple CPU cores so that tasks can literally run at the exact same time. A parallel system has actual physical overlap rather than the illusion created by scheduling. Both concurrent and parallel systems must handle race conditions, mutual exclusion, and synchronization, but the challenges are more visible in parallelism because tasks truly run simultaneously. In concurrency, even though only one task runs at a time, shared data can still be accessed inconsistently across switches, so locks and protection mechanisms are still required. The main difference being concurrency aims to execute multiple tasks on one CPU core, while parallel execution makes use of multiple cores.


Q2. In 4.4, let’s suppose that a task has executed its budget (execution time of C per T). Explain the task’s behavior afterwards.

When a task consumes more than its reserved computation budgets within its current period, the kernel does not immediately kill, stop, or throttle the task. Instead, the task continues running, and the system records the excess usage in the task’s computation-time accumulator. At the next period boundary (when the task calls wait_until_next_period and the hrtimer fires), the kernel does the following. Resets the accumulator for the new period. Wakes the task if it has blocked waiting for the next period. Logs the overrun, as required in Section 4.5, by printing the formatted “budget overrun” message.  With section 4.6 extending the functionality to send SIGUSR1 to the task so the user-space program can react to the overrun. Once all this happens, the task starts its next period normally. The extra execution from the previous period does not carry over unless additional logic is implemented. An overrun does not immediately stop the task, the kernel records it, reports it, and then resumes standard periodic behavior at the beginning of the next period. 


Q3. If a deadline of a periodic task is different with its period, how do you implement to support real-time?

	When a periodic task has a deadline D that is different from its period T, we must support arbitrary-deadline periodic tasks instead of assuming the implicit deadline model(where D = T). To do so, the reservation system must track the release time of each job, period T, which determines job arrival times, and relative deadline D, which determines when each job must finish. The deadline of each job is then computed as absolute deadline = release time + relative deadline (D). The hrtimer and wake-up logic still use T to determine when the next job begins, but the scheduler must become deadline-aware so that jobs are ordered according to their deadlines, not their periods. The scheduling approaches used for such an instance often consist of implementing Earliest Deadline First (EDF) for general arbitrary deadline tasks, or Rate Monotonic when the system guarantees that the deadline is greater than or equal to the period for all tasks. Budget enforcement (C per period) and accumulator resets still occur every T, but overrun checks must be compared against D. This is because the job’s validity window is based on its deadline opposed to its period. Job releases are driven by periods, while job deadlines are driven by deadlines. To support real-time implementations in this scenario, EDF or Linux’s SCHED_DEADLINE can be used, as they prioritize tasks based on their absolute deadlines.
