Q2. How does a system call execute? Explain the steps from making the call in user-space process to returning from the call with a result. 

A system call starts from the user space. The user space wants access to the hardware but has no means of getting there, so the system call procedure allows the kernel to access the hardware on the users behalf. From the user space, a trap or interrupt happens, indicating that a system call is to be made. Once the trap or interrupt is created, mode switching commences, where the system attempts to go from user mode to kernel mode, to the exact system call that is needed for that functionality. If everything is correct the kernel then enters the system call and executes the critical section and places any return values into a designated register. Once the system call finishes we mode switch back to user space where it has access to the new result. 

Q3. What is SYSCALL_DEFINEx and where is it defined?

SYSCALL_DEFINEx is the convention used by Linux to identify different system call structures that may take place with x being the number of argument that it can have. So as x increases, the number of arguments increase. This allows for consistency in format and structure of system calls, and allows for better ease of use between systemcalls and syscall table. It is defined in the Linux kernel syscalls.h header file. For our calc system call, we used SYSCALL_DEFINE4 because it takes 4 parameters: SYSCALL_DEFINE4(calc, int, param1, int, param2, char, operation, int __user *, result)

Q5. What issues have you faced with the project and how did you resolve them?

With system calls being a foreign concept to the group, the most challenging part was ensuring our understanding of how to properly and safely implement system calls and context switches for loadable kernel modules. Early challenges included Makefile and Kbuild structure issues, particularly ensuring TAB characters rather than spaces in command lines and maintaining proper directory organization. We also encountered kernel configuration problems where modules failed to compile due to missing headers. These were resolved through careful attention to make syntax, proper use of the provided config file, and running necessary preparation steps before building. Additionally, our calc system call initially wasn't recognized because sys_calc.c wasn't being compiled into the kernel despite existing in our directory - this required ensuring proper build order and references in both Kbuild and the root Makefile. 

The most significant challenge was getting the mod_calc module to work without causing kernel panics. Our initial implementation used x86-specific memory protection code that doesn't exist on ARM architecture, requiring a complete rewrite. Even after fixing architecture-specific issues, we faced crashes because modern kernels protect the syscall table from modification as a security feature. We explored several approaches, from trying various memory protection APIs to temporarily disabling kernel-wide protections through configuration changes. Our final solution used kallsyms_lookup_name() to dynamically locate kernel functions for controlled, temporary write access to protected memory. This proper API approach allowed safe syscall table modification without compromising system-wide security, combined with corrected pointer types and proper synchronization to prevent race conditions. 

Beyond code challenges, we faced practical issues with cross-compilation and file transfer between Ubuntu and the Raspberry Pi. We resolved this using SD card mounting methods from Project 1, though VMware USB connectivity required troubleshooting. Terminal crashes during sudo operations also necessitated workarounds like opening fresh terminals or restructuring workflows to minimize interactive prompts. Most resolutions came from our collaborative approach of comparing individual implementations, group discussion, researching kernel documentation, and systematic trial and error. The project taught us valuable lessons about kernel development, the importance of understanding architecture-specific differences, proper synchronization mechanisms, and how modern kernels implement security protections. We learned that kernel development requires careful attention to build procedures, thorough debugging, and a deeper understanding of low-level system mechanics.
